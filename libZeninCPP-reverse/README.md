# Реверс нативной библиотеки `libZeninCPP.so`

Глубокий разбор нативной библиотеки приложения **Zenin External** (чит-лоадер,
замаскированный под `com.reddit.frontpage`). Именно здесь спрятана вся реальная
логика — Java-код защищён Dex2C и переадресует вызовы в эту `.so`.

Анализируются обе ABI из APK:
- `lib/arm64-v8a/libZeninCPP.so` (6 016 400 байт) — основная (телефоны)
- `lib/x86_64/libZeninCPP.so` (6 102 456 байт) — для эмуляторов

## Структура папки

| Папка/файл | Содержимое | Инструмент |
|-----------|-----------|-----------|
| `disasm/x86_64-full-disasm.asm` | Полный дизассемблинг x86_64-версии (~1.36M строк, Intel-синтаксис) | objdump (binutils 2.42) |
| `disasm/x86_64-readelf-all.txt` | Полный ELF-разбор x86_64 (секции, символы, релокации) | readelf |
| `disasm/arm64-readelf-all.txt` | Полный ELF-разбор arm64 | readelf |
| `disasm/arm64-dynamic-symbol-table.txt` | Таблица динамических символов arm64 | objdump -T |
| `ghidra-decompiled/all_functions.c` | **C-псевдокод 2173/2273 функций** (26 МБ) | Ghidra 12.1.2 headless |
| `ghidra-decompiled/{symbols,defined_strings,functions_index}.txt` | Символы, строки, индекс функций | Ghidra |
| `info/NATIVE-ANALYSIS.md` | Итоговый разбор по декомпиляции | вручную |
| `info/` | Сводки, карта JNI, заметки | вручную |

> Примечание: системный `objdump` собран без поддержки aarch64, поэтому полный
> дизассемблинг сделан по **x86_64**-версии (бинарно эквивалентный код),
> а C-декомпиляция — по **arm64** через Ghidra. Так покрыты обе архитектуры.

## Что уже установлено по нативному коду

### `JNI_OnLoad` (точка входа JNI)
Маленькая функция:
1. `GetEnv` с версией `0x10006` (**JNI 1.6**);
2. передаёт управление внутренней init-функции (в x86_64 — `0x3fcf0`);
3. возвращает `0x10006`.

### Init-функция рантайма Dex2C (`0x3fcf0`)
- Вызывает виртуальный метод по смещению `[obj+0x720]` (объект C++-рантайма);
- массово копирует таблицу указателей из `.data.rel.ro` (`0x5c23a8…`) в глобальный
  массив (`0x5d9540…`) — это построение таблиц диспетчеризации нативных методов
  и дешифровки строк.

### Регистрация нативных методов
Выполняется **динамически** через таблицу функций `JNIEnv` (косвенные вызовы
`call [reg+off]`), а не по именам через PLT — поэтому в библиотеке нет символов
`Java_*` и явного импорта `RegisterNatives`. Это штатный приём Dex2C/VMP для
сокрытия соответствия «нативная функция ↔ Java-метод».

### Сетевой/крипто-слой (из строк ELF)
`HttpURLConnection`, `HttpsURLConnection`, `X509TrustManager`/`TrustManager`
(кастомный/ослабленный TLS), `javax.crypto.spec.SecretKeySpec` — онлайн-проверка
лицензионного ключа `ZE-********` с шифрованием.

## Ограничения статики
Строки зашифрованы и расшифровываются в рантайме нативными подпрограммами, а имена
методов скрыты. Чтобы вытащить конкретный сервер авторизации, формат запроса и
целевой пакет игры, нужен **динамический анализ (Frida)**: перехват дешифратора
строк, `RegisterNatives` и HTTP(S)-запроса авторизации на реальном/эмулированном
устройстве.

## Воспроизведение
```bash
# Дизассемблинг x86_64
objdump -d -M intel lib/x86_64/libZeninCPP.so > x86_64-full-disasm.asm
readelf -a       lib/x86_64/libZeninCPP.so > x86_64-readelf-all.txt
# C-декомпиляция arm64 (Ghidra headless)
analyzeHeadless <proj> zenin -import lib/arm64-v8a/libZeninCPP.so \
  -postScript ExportDecompiledC.java <outdir> -deleteProject
```
